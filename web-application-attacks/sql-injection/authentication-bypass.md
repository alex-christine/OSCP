# Authentication Bypass

## Basic Authentication Bypass

From a high level, if a SQL query is being constructed using the variables coming in from a login page (or other authentication portal), there is a potential to craft a malicious query that will return a false valid result.

### Example

Consider the example from [Identifying SQLi Vulnerabilities](identifying-sqli-vulnerabilities.md). The authentication query was constructed in PHP via concatenation:

```php
$query = "select * from users where username = '$user' and password = '$pass'";
```

Which in normal operation would look like:

```sql
select * from users where name = 'tom' and password = 'jones';
```

But consider the malicious attacker's submission for `$user` (Value: `tom' or 1=1;#'`) which would yield a query of :

```sql
select * from users where name = 'tom' or 1=1;#' and password = 'jones';
```

The `#` symbol comments out the remainder of the line and thus would create a query that is always true (`or 1=1`) and would thus create a "valid" password check and return all user records.

Simply returning all records may not be enough to complete authentication bypass, what happens next depends on the applications code. Because of the black box nature of SQLi hunting/testing the only thing that an attacker can do is trial and error.

Some programming languages have functions that query the database and expect a single record. If these functions get more than one row, they will generate an error. Other functions might process multiple rows just fine.

If errors are being generated by multiple lines returned from the query the return can be limited by including `LIMIT 1` in the injected SQL (`tom' or 1=1 LIMIT 1;#'`) to yield the query:

```sql
select * from users where name = 'tom' or 1=1 LIMIT 1;#' and password = 'jones';
```

Testing this agains the Windows 10 lab machine results in successful authenticaion bypass. To understand why, consider the excerpt from the `/login.php` function of the application:

{% code title="login.php" overflow="wrap" lineNumbers="true" %}
```php
<?php
  session_start();
  include "database.php";
  if ( ! empty( $_POST ) ) {
    if (isset($_POST['username']) && isset($_POST['password']) ) {
      $sql="select * from users where username ='" . $_POST['username'] . "' and password = '" . $_POST['password'] . "'";
      $result = $conn->query($sql);
      if(!$result) {
        trigger_error("invalid query: " . $conn->error);
      }
      if( $result->num_rows == 1 ) {
        $_SESSION['user'] = $_POST['username'];
        header("Location:admin.php");
      } else {
        echo "<div class=\"alert alert-danger\">Wrong username or password</div>";
      }
    }
  }
?>
```
{% endcode %}

On line 6, the values of the `username` and password parameters submitted via POST are directly added to the string containing the SQL query. Normally, the query would only return results when a valid username and associated password are submitted. However with the malicious injected payload the password check is bypassed, and the return is limited to a single row thus creating a "valid" login.
